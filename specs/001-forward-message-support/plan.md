# Implementation Plan: 合并转发消息解析与 JSON 化消息格式

**Branch**: `001-forward-message-support` | **Date**: 2026-05-31 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-forward-message-support/spec.md`

## Summary

实现 QQ 群机器人的合并转发消息（OneBot 11 `get_forward_msg` API）解析能力：检测 `forward` 消息段、递归获取嵌套内容（最大深度 3）、统一使用 JSON 格式作为 LLM 输入/输出的消息载体。改造 pipeline.py 的消息解析和 prompts.py 的系统提示词，新建 `forward.py` 模块专门处理合并转发逻辑。

## Technical Context

**Language/Version**: Python 3.12+

**Primary Dependencies**: NoneBot2 (OneBot V11 adapter), LangChain/LangGraph, nonebot_plugin_localstore

**Storage**: JSON 文件存储（data/hatsume-plugin/memory.json, likes.json）

**Testing**: pytest（现有测试框架）

**Target Platform**: Linux/macOS 服务器（Python 运行时，QQ Bot 后端）

**Project Type**: QQ 群机器人插件（NoneBot2 插件）

**Performance Goals**: 合并转发解析延迟 < 3s（含 API 调用）；不影响现有消息处理的 debounce 时间（5s）

**Constraints**: 最大嵌套深度 3；API 调用超时 10s；递归调用必须包含超时保护

**Scale/Scope**: 单群 ~500 人；日活消息 ~2000 条

## Phase 0: Research

No unresolved unknowns. Design decisions already made during brainstorming:

| Decision | Rationale |
|----------|-----------|
| JSON format unified messages | LLM 易于解析结构化信息；type 字段区分消息类型 |
| `forward.py` 独立模块 | 职责分离：pipeline 负责普通消息，forward 负责转发 |
| 递归解析 + depth 截断 | 保持树形结构的同时防止无限递归 |
| depth 从 0 开始计数 | 顶层转发消息本身 depth=0 隐含，嵌套子消息 depth=1 |
| `bot.call_api("get_forward_msg", id=...)` | NoneBot 标准 API 调用方式 |

### OneBot 11 `get_forward_msg` API 数据流

```text
Event Message
  ├── segment(type="text", data={"text": "..."})
  ├── segment(type="image", data={"url": "...", "file": "..."})
  └── segment(type="forward", data={"id": "xxx"})  ← 检测点
        │
        ▼ bot.call_api("get_forward_msg", id="xxx")
  API Response (array of nodes):
  [
    {
      "user_id": 111,
      "nickname": "张三",
      "content": [...]    ← 消息段数组（text, image, forward, ...）
    },
    {
      "user_id": 222,
      "nickname": "李四", 
      "content": [
        {"type": "forward", "data": {"id": "yyy"}}  ← 嵌套转发！
      ]
    }
  ]
```

## Phase 1: Design

### Data Model

See [data-model.md](./data-model.md) for full entity definitions.

Key entities:
- **MessageJSON** — `{type, time, user{id,name}, content, reply_to?, messages?, depth?}`
- **ForwardNode** — API 返回的原始节点 `{user_id, nickname, content}`
- **LLMOutputJSON** — `{message: str}`

### Interface Contract

**`forward.py` 模块接口：**

```python
# 检测消息中是否有 forward segment
def has_forward_segment(msg: Message) -> str | None

# 递归解析合并转发
async def parse_forward_messages(
    bot: Bot, forward_id: str, depth: int = 0
) -> list[dict]

# 一站式检测+解析
async def resolve_forward_content(
    bot: Bot, msg: Message, depth: int = 0
) -> list[dict] | None
```

**`utils.py` 新增函数：**

```python
def message_to_json(
    user_name: str, user_id: int,
    content: str | list[dict],
    msg_time: str,
    reply_to: dict | None = None
) -> dict
```

**`pipeline.py` 输出变更：**
- text content 从 `generate_msg_template()` 输出改为 `json.dumps(msg_dict, ensure_ascii=False)` 输出
- 接口不变：仍返回 `(content_parts, source_entry)`
